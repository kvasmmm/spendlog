# Проверка SpendLog

Дата: 22 октября 2026, Asia/Seoul. Отчёт относится к текущим исходникам, а не к ранее объявленным результатам.

## Итог и границы

Проект доработан на месте, без сброса рабочей базы. Тесты и импорт настоящего файла выполнялись только на временных SQLite. Готовность к ежедневному использованию **не подтверждена**: полноценная frontend-сборка, запуск контейнеров и физический iPhone остаются непроверенными.

## Среда и реально выполненные проверки

- Прочитаны README, предыдущий VERIFICATION, модели, схемы, API, миграция, существующие тесты, frontend и deployment-конфигурация.
- Обычная установка закреплённых зависимостей через pip/npm не удалась: сеть/DNS ограничены; для npm зафиксирован `EAI_AGAIN`. Закреплённые версии не менялись ради успешного теста.
- Из **локального кеша** собрана отдельная временная среда: Python **3.12.14**, FastAPI **0.141.1**, SQLAlchemy **2.1.1**, Pydantic **2.13.5**, Alembic **1.20.0**, pytest **9.1.1**, httpx **0.28.1**, Starlette **1.7.0**. FastAPI, SQLAlchemy и Pydantic отличаются от requirements.txt; результат не заменяет проверку закреплённого окружения.
- **60 pytest cases прошли**, последний полный прогон — 31.69 s. В sandbox не доставлялось межпоточное пробуждение asyncio: даже минимальный `portal.call(lambda: 42)` зависал. Временный тестовый раннер добавлял таймер event loop 10 ms; приложение, HTTP/API, финансовая логика и SQLite не подменялись. Обычный `python -m pytest -q` в этой среде без раннера зависает на входе в TestClient. На нормальном хосте следует запускать стандартную команду.
- Сохранились существующие 25 cases; добавлены 35 cases для банка, сверки, меню, категорий, каталогов и миграции непустой базы.
- Alembic: fresh upgrade → check → downgrade → upgrade; отдельно upgrade старой непустой схемы → check. Существующие Product/Payment сохраняются, общий справочник заполняется, created_at старых платежей восстанавливается из их occurred_at. Downgrade при наличии истории банка намеренно запрещён, чтобы не потерять происхождение.
- `compileall` для backend успешен.
- TypeScript: доступным локальным компилятором выполнены синтаксическая транспиляция TS/TSX и частичная проверка типов с настоящими React types. Локальных ошибок не обнаружено; **23 диагностики отсутствующих внешних зависимостей/связанных implicit-any исключены**, поэтому это **не полный typecheck**. `npm run build` остаётся непроверенным.
- Выполнен `frontend/scripts/test-helpers.mjs` с доступным локальным TypeScript: постоянный черновик, повреждённый JSON/структура, запрет localStorage/sessionStorage, восстановление через fallback, очистка при logout и UUID для HTTP (10 000 уникальных UUID v4).
- Обнаружен и исправлен конфликт CSP: инициализация темы перенесена из inline-script в public/theme.js, разрешённый существующим nginx `script-src 'self'`.
- `docker compose config --quiet` успешен. Запрос `docker compose up -d --build` выполнен, но **отклонён доступом к `/var/run/docker.sock`**. sudo также запрещён средой. Контейнеры не собраны и не запущены агентом.
- Для нативного запуска на свежей временной БД миграции прошли; Uvicorn выполнил startup, затем завершился из-за запрета bind `127.0.0.1:18080`. Проверки HTTP сделаны через TestClient, не по живому порту.
- `/usr/bin/gh repo create SpendLog --private …` запрошен, но завершился `error connecting to api.github.com`. Действительность сохранённого токена независимо не подтверждена. Репозиторий **не создан и не запушен**. Локальный `.git` в среде доступен только на чтение. Подготовлен проверенный `bash -n` скрипт публикации исходников; токен не выводился.
- Добавлен GitHub Actions workflow для стандартных зависимостей, backend-тестов, frontend helpers/build и фактического Compose smoke test. Workflow **ещё не запускался**.

## Настоящая PDF iM Bank

Файл прочитан до написания парсера; личная PDF исключена из Git. В репозиторий входят только синтетические обезличенные примеры формата.

В реальном файле обнаружены 145 строк, время до секунды, отдельные колонки списания/зачисления и остаток. Стабильного банковского ID нет; NO — номер строки. Проверена непрерывность всей цепочки остатков и полнота страниц.

На отдельной временной БД выполнен **полный API-сценарий с настоящими PDF-байтами и настоящим pdftotext**, без подмены извлечения:

1. Вход → PDF preview → 145 новых строк; до подтверждения движений нет.
2. Атомарное подтверждение всех строк.
3. Проверка расходов, денежного потока и отсутствия автоматического дохода за оба финансовых периода, затронутых выпиской.
4. Повторная загрузка и подтверждение того же файла: финансовые итоги не меняются.
5. Экспорт и повторный импорт полного JSON: added = 0.

Проверка завершилась успешно; пользовательская БД и Docker volume не затрагивались. Вторая настоящая пересекающаяся выписка пока не предоставлена: пересечения проверены синтетическими примерами того же формата, не двумя реальными экспортами банка.

## Финансовые сценарии в тестах

- Доход, ручной расход, смешанные категории, точное распределение целых вон и нулевые покупки.
- Разделённый чек, частичные возвраты, переплата, возврат до долга, возмещение без нового дохода.
- Займы в обе стороны, исправление/удаление займов и возвратов, запрет удаления уже погашаемого долга.
- Исторические цены разных магазинов и категории сохраняются после изменения каталога.
- Повторы Idempotency-Key и конфликт изменённого тела, конкурирующие покупки и погашения, устаревшие версии.
- JSON/CSV roundtrip и повтор без дублей, атомарный откат повреждённых копий; совместимость старого JSON v1.
- Корейская граница 21/22 числа, настройка начала месяца, новый год и високосный февраль.
- Тот же банковский файл дважды, другой физический порядок строк и обратная выгрузка с перенумерацией.
- Пересекающиеся периоды: старые строки пропускаются, новые добавляются.
- Две настоящие покупки с одинаковыми временем, суммой и магазином, но разными остатками сохраняются отдельно.
- Одиночное совпадение без контекста требует ручного решения; изменённое описание не переписывает прошлое; изменённые сумма/направление/время нельзя молча пропустить как повтор.
- Ошибка посередине импорта и конфликт связи откатывают все уже созданные движения.
- Два одновременных подтверждения создают один набор; устаревший preview требует обновления.
- Разные банковские счета не делят идентичность операций.
- Поступление не становится доходом автоматически; явная классификация дохода/перевода, версии и защита банковских платежей от случайного удаления.
- Связь/отмена/повторная связь чека сохраняют источник, личную долю, долг и время создания ручного Payment. Лишнее списание удаляется; реальные времена банка и чека различимы.
- Связь через границу финансового месяца: потребление остаётся по времени чека, денежный поток — по времени банка.
- Неоднозначные кандидаты не связываются сами.
- Резервные копии банковских связей в JSON/CSV, повтор и сохранность данных после закрытия/повторного открытия соединений SQLite.
- Общий справочник не содержит цены/магазина; личные переименования его не меняют; повтор создания того же личного товара безопасен.

## Что не проверено и не реализовано

- Production TypeScript/Vite build с установленными зависимостями, фактическая Docker-сборка, nginx/Caddy/TLS, рестарт настоящего Docker volume, сетевой доступ с телефона.
- Визуальная mobile-first проверка и полноценный браузерный E2E. Вёрстка предпросмотра, формы и навигация адаптированы по исходникам; визуальная приёмка не выполнена.
- Физический iPhone/Safari: камера, реальные штрихкоды, PWA, мобильная клавиатура и поведение localStorage после закрытия приложения.
- PostgreSQL не запускался.
- Второй реальный PDF с перекрывающимся периодом и другие варианты банковского формата не проверены.
- Автоматическая сверка банковских поступлений/списаний с ручными займами и возвратами, исправление финансовых полей уже импортированной строки, OCR и банковские CSV/XLS пока не реализованы.
- Общий каталог — отдельная таблица той же БД; полноценный multi-user, роли публикации и модерация пока не реализованы.
- Автоматические внешние backup с ротацией и проверкой восстановления остаются следующим этапом. Существующий SQLite Online Backup скрипт не заменяет такую систему.
- Одно предупреждение Starlette о deprecated httpx TestClient; это предупреждение тестового клиента, не ошибка финансового API.

## Проверка на пользовательском хосте

Сначала сохраните текущий JSON через настройки и SQLite-снимок, если backend уже запущен:

```bash
sudo docker compose exec -T backend python < scripts/backup.py
```

Не удаляйте volume. Затем:

```bash
sudo docker compose up -d --build
sudo docker compose ps
sudo docker compose logs --tail=100 backend web
```

1. Открыть HTTPS-ссылку в Safari, войти, переключить тему; нажать «+», проверить сохранение и повторное открытие черновика.
2. Найти известный и неизвестный штрихкод; цена из общего справочника не должна подставляться как чужая цена.
3. В «Банк» загрузить PDF: проверить 145 строк и решения, особенно переводы/займы и поступления.
4. Создать подходящий ручной чек, выбрать его в preview или выполнить ручную связь позже; проверить личный расход и единственное списание.
5. Повторить загрузку: итоги не должны измениться. Затем проверить вторую настоящую расширенную выписку.
6. Отменить/восстановить связь; проверить историю, суммы и даты. После отмены два несопоставленных движения существуют до повторной сверки.
7. Экспортировать JSON/CSV и импортировать обратно: added = 0. Проверить после рестарта Compose без удаления volume.
8. Проверить офлайн-ошибку, закрытие/повторное открытие приложения, отказ камеры, мобильную вёрстку и PWA.

Приватная публикация после проверки GitHub-авторизации на хосте:

```bash
bash scripts/publish-private.sh SpendLog
```

Скрипт не отправляет банковскую PDF, `.env`, БД и выгрузки, не меняет существующий origin. Фактический результат публикации проверяется отдельно.

## Переработка предпросмотра PDF — 22 октября 2026

- Вместо 140 раскрытых карточек показаны свёрнутые группы по названию с количеством, направлением и суммой. Филиалы GS25 и CU имеют общие названия для отображения; исходные строки не меняются.
- Добавлены сводка новых сумм, поиск, фильтры всех/спорных/списаний/поступлений/повторов. Строки и их поля редактирования раскрываются отдельно. История и список сохранённых операций свёрнуты.
- Массовая классификация группы применяется только к обычным новым строкам без кандидатов сверки. Повторы, неоднозначные строки, выбранные связи и отрицательные суммы при выборе дохода защищены от такого изменения.
- Helper-тесты прошли: группировка филиалов, разделение направлений, точные суммы без схлопывания строк, фильтры, начальные решения, массовые действия без перезаписи спорных/связанных строк и без мутации исходных данных. Существующие тесты черновика/UUID также прошли. Backend и API-контракт не менялись.
- На настоящей PDF проверено: 145 строк превращаются в 35 свёрнутых групп; число исходных операций и общая сумма полностью сохраняются.
- Синтаксическая транспиляция TS/TSX и частичная проверка типов выполнены доступным компилятором. Полная сборка и визуальная проверка на iPhone по-прежнему не подтверждены: зависимости frontend в этой среде отсутствуют.
- Проверка на устройстве: загрузить PDF → увидеть группы GS25/DGIST и сводные суммы → раскрыть одну группу → применить «Переводы» к её новым строкам → проверить, что спорные строки остались в «Нужно решить» → подтвердить импорт.

## Меню, детализация банковских списаний и новая палитра

- Добавлены приватные карточки меню без штрихкода: заведение, блюдо, цена за порцию, категория и контроль версий. Можно создать карточку заранее или во время заполнения чека. Исторические цены/названия/категории хранятся в Item; изменение меню их не переписывает. Меню не попадает в общий справочник штрихкодов.
- У отрицательной банковской операции появилось «Добавить блюда / товары». Создание чека и связь выполняются одной транзакцией с Idempotency-Key, проверкой версии и точным совпадением банковской суммы. При ошибке остаётся исходный платёж, без половины чека.
- Связанные чеки теперь можно редактировать без отмены связи, если итог остаётся банковским. Сохраняются ID, created_at и фактическое время банковского Payment; долги пересчитываются. Редактирование при уже внесённых возвратах по-прежнему блокируется.
- На dashboard добавлена аналитика по заведениям: количество конкретных блюд/товаров и личные расходы за выбранный финансовый месяц. Суммы банковских списаний без позиций показываются отдельно. Тестовый сценарий: общий расход 100 000 ₩, 3 тонкатсу, 6 чикенмайо и 40 000 ₩ пока без детализации. Количество относится ко всему чеку, личная доля денег — только к владельцу.
- Добавлены категории еды вне дома, магазинов у дома, обязательных трат, страховки, связи/интернета, подписок и здоровья/клиник. Категорию банковского списания можно выбрать до импорта, массово для группы и после импорта. После связи приоритет у категорий позиций.
- Миграция c83e102d5a61 добавляет menu_products, необязательную связь Item и категорию BankTransaction. Непустые items не пересоздаются в SQLite. Проверена сохранность существующих ID, цен, количеств, платежей и foreign keys. Архив JSON/CSV обновлён до v3, импорт v1/v2 поддерживается.
- Палитра заменена на нейтральные поверхности с индиго-акцентом: белая/светло-серая тема и тёмно-синяя/графитовая. Обновлены графики, формы, навигация, состояния, SVG и сгенерированные из SVG PNG-иконки, PWA theme/background colors.
- Полный backend-прогон: 60 passed (31.69 s) в описанной выше среде из кеша; миграции и импорт настоящей PDF также прошли на временных SQLite.
- Frontend helpers дополнены проверкой безопасного назначения категории группе и восстановления черновика с menu_product_id. Синтаксическая транспиляция TS/TSX и частичная проверка типов проходят; это не полная production-сборка.
- Визуальная проверка на Safari/iPhone и сборка контейнеров всё ещё не выполнены из-за ограничений среды. Для обновления нужны и backend, и frontend; пересборки только web недостаточно. sudo из встроенной команды чата не может запросить пароль без терминала — пароль нужно вводить в обычном терминале компьютера, не отправлять в чат.

Приёмка: «Каталог → Моё меню → Карточка» (заведение, тонкатсу, цена) → «В покупку» (количество 3, добавить в чек) → сохранить. Либо «Банк → Банковские операции → Добавить блюда / товары» → заполнить позиции до точной суммы списания. Затем «Обзор → Что покупал в каждом месте» → раскрыть заведение. Проверить изменение карточки меню, редактирование состава связанного чека и повторное сохранение без нового списания.
